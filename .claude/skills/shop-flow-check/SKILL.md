# 구매 흐름 점검

## 먼저: 실제 주문을 만들지 않는다

로컬 `npm run dev`도 `.env.local`의 **운영 Supabase와 Resend**를 쓴다. 체크아웃을 제출하면 `orders`에 실제 행이 생기고, 구매자와 운영자에게 실제 메일이 나간다.

- 기본 범위는 **제출 직전까지**다. 제출 버튼은 누르지 않는다.
- 제출 이후(주문 완료 화면, 메일, 관리 화면의 주문 탭)를 봐야 하면 사용자에게 먼저 묻는다. 승인받으면:
  - 수신 이메일은 사용자가 정해 준 주소를 쓴다.
  - 이름에 `[TEST]`를 붙이고, 주문 번호를 보고한다. 테스트 주문의 삭제도 사용자 승인 사항이다.
- 프로덕션(abovemin.com)에서는 조회만 한다.

## 준비

```bash
cd frontend && npm run dev   # 백그라운드로
```

Playwright MCP로 진행한다. 뷰포트 두 개를 모두 본다: 모바일 390×844, 데스크톱 1440×900. 모바일이 기준이다.

## 단계별로 볼 것

1. **`/shop`** — 판매 중 상품만 보이는지(`draft`는 숨김, `sold_out`은 표시만). 판매 가능한 상품이 하나도 없으면 예고 화면이 나오는 것이 정상이다. 카드의 담기 버튼은 40px 원이다.
2. **`/shop/[id]`** — 갤러리 전환, 옵션 선택에 따라 가격이 바뀌는지, 품절 옵션이 선택되지 않는지, 옵션을 고르기 전 담기가 막히는지.
3. **담기** — 같은 상품·옵션을 다시 담으면 줄이 합쳐지는지, 상단 Bag 숫자가 맞는지, 새로고침해도 유지되는지.
4. **`/cart`** — 수량 증감과 삭제, 합계, 빈 장바구니 화면과 그곳에서 샵으로 돌아가는 길.
5. **`/cart/checkout`** — 여기까지가 기본 범위.
   - 각 입력의 `type` / `inputMode` / `autoComplete`(이름, 이메일, 전화, 우편번호, 주소)이 모바일 키보드와 자동완성에 맞는지.
   - 빈 값과 잘못된 값의 오류가 그 입력 옆에, 무엇을 고치라는 말로 보이는지.
   - 주문 요약의 합계가 장바구니와 같은지. 입금 안내(계좌이체)가 제출 전에 보이는지.
   - 제출 버튼이 화면 키보드에 가려지지 않는지, 터치 타깃이 충분한지.
6. **콘솔과 네트워크** — 오류, 실패한 요청, 4xx/5xx가 없는지.

## 서버 쪽은 테스트로

브라우저로 확인하지 않는 것(가격 재계산, 멱등 키, 레이트 리밋, 메일 본문)은 단위 테스트가 잠근다:

```bash
npm test -- order-items orders-schema cart-lines price product order-email rate-limit
```

## 보고

단계별로 통과/문제를 적고, 문제는 뷰포트·재현 순서·스크린샷과 함께 낸다. 제출을 하지 않았다면 "제출 이후는 확인하지 않음"이라고 분명히 쓴다.
